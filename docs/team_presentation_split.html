👤 Member 2: Routing Algorithms & Math Lead
Algorithms & Math (~3 Mins)
Core Concepts to Explain:
  • Why Normalization is Required: Milliseconds (e.g. 60ms), percentages (e.g. 18%), and administrative costs cannot be summed directly. NetResQ normalizes each metric into dimensionless [0, 1] scales.
  • Normalization Formulas: norm_lat = lat / 50ms, norm_loss = loss% / 100, norm_util = util% / 100.
  • Composite Cost Formula: link_cost = (w_cost × C) + (w_lat × norm_lat) + (w_loss × norm_loss) + (w_util × norm_util).
  • Proof of Dijkstra Correctness: Since all weights ≥ 0 and metrics ≥ 0, and cost floor is 0.001, no negative cycles can exist. Dijkstra is mathematically guaranteed to find the global minimum cost.
  • Worked Example (H1 → H4): Path A (Direct S1-S3, 18% loss): Cost = 6.12.
    Path B (Detour via S2, 0% loss): Cost = 4.79.
    Quality-Aware picks Path B because 4.79 < 6.12, saving 54ms delay and 18% loss!

Speaking Script / Pitch:
"I am [Name], and I will explain the mathematical core of NetResQ. To overcome static hop counting, we developed a multi-metric composite cost function. Because milliseconds and percentages have incompatible units, we first normalize latency against a 50ms reference, and loss and utilization into decimals between 0 and 1. We weight packet loss higher at 2.0 to aggressively penalize drop-prone links. Crucially, because all edge costs are strictly positive (≥ 0.001), Dijkstra's algorithm is mathematically guaranteed to find the global optimum. As seen on our screen, when direct link S1-S3 degrades, our formula proves that a 4-hop clean path has a lower composite cost (4.79) than a degraded 3-hop path (6.12). Key Viva Questions & Answers:
Q: Why not use Bellman-Ford instead of Dijkstra?
A: Bellman-Ford is slower (O(V × E)) and only needed for negative edge weights. Because our composite cost function guarantees strictly positive costs, Dijkstra (O(E + V log V)) is faster and globally optimal.
👤 Member 3: Self-Healing Engine & API Specialist
Failover & Backend (~3 Mins)
Core Concepts to Explain:
  • Failure Handling: Failed links are marked DOWN in the authoritative simulation adapter. Graph building skips them: if link.status == 'down': continue.
  • Automated Failover: Dijkstra recalculates active routes in sub-millisecond time (~0.48ms).
  • Monotonic Clock Benchmarking: Measures recalculation time via Python's time.perf_counter().
  • Network Partition Handling: If all paths fail, networkx.has_path() returns False; API cleanly returns status "no_path" without crashing.
  • FastAPI Endpoints: GET /api/topology, POST /api/links/{id}/fail, POST /api/links/{id}/restore, GET /api/events.

Key Viva Questions & Answers:
Q: What is the difference between software rerouting time and physical recovery time?
A: Software route computation (~0.5ms) is CPU time to prune the graph and run Dijkstra. Physical recovery in hardware includes carrier loss detection and OpenFlow OFPFlowMod rule installation (typically 20ms to 100ms).

Key Viva Questions & Answers:
Q: How does LLDP discovery work in an SDN controller like Ryu?
A: The controller sends LLDP packet-out messages to all switch ports. When neighbor switches forward the packet-in back to the controller, the controller maps the adjacency between switch datapath IDs and port numbers.
